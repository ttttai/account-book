# 共有データの反映（他メンバーの変更の自動反映）

状態: 承認済み

バージョン: 0.1.0

## 1. 目的と範囲

同じグループの別メンバーが登録・編集・削除した取引を、利用者が画面を開いたまま何もしなくても、ある程度早く（目標60秒以内）ホーム・履歴・分析へ反映する。二重登録と「相手の入力がまだ出ない」混乱を減らすことが目的であり、即時性（Realtime）は求めない。

対象要件は`SYNC-001`〜`SYNC-006`、受け入れ条件は`AC-SYNC-001-1`〜`AC-SYNC-006-2`とする。Realtime subscription（`D-010`）、Service Worker、プッシュ通知（`NFR-PWA-004`）は引き続き延期し、本仕様はそれらの前段となる「軽量な変更確認と再取得」だけを定義する。

## 2. 用語

| 用語         | 定義                                                                                                                             |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 変更token    | グループ所有データの現在状態から決定的に導く不透明な文字列。値が変われば何かが変わったことだけを示し、内容・件数・金額を表さない |
| 変更確認     | 変更tokenを取得して前回値と比較する処理。取引データを読まない                                                                    |
| 再取得       | Next.jsの`router.refresh()`によるServer Componentの再描画。Client Componentの状態とURLは保持される                               |
| 自動反映画面 | 変更確認と再取得を行う画面。ホーム、履歴、概要分析、詳細分析                                                                     |

## 3. 要件

- `SYNC-001` 自動反映画面を表示中、他メンバーによる取引の作成・編集・削除、定期取引の作成・編集・終了、カテゴリの変更を、利用者の操作なしに目標60秒以内で反映する。
- `SYNC-002` 画面が非表示（他タブ、ホーム画面、スリープ）から表示へ戻ったとき、直ちに変更確認を行う。非表示の間は変更確認を行わない。
- `SYNC-003` 変更確認は認証とアクティブ所属を毎回確認する軽量なRoute Handlerで行い、取引データを返さない。変更がない間はServer Componentの再取得を行わない。
- `SYNC-004` 再取得はroute-levelのloadingを表示せず、表示中の月・集計対象・選択日・絞り込み条件・スクロール位置・入力中の値を失わせない。
- `SYNC-005` 取引入力・編集、設定ハブ、メンバー、カテゴリ、定期取引の画面では変更確認と自動反映を行わない。
- `SYNC-006` Realtime subscription、Service Worker、プッシュ通知、polling専用のDBテーブル・job・queueを使わない。

## 4. 変更token

### 4.1 算出

変更tokenは、選択中グループの次の集約値から決定的に導く。

| テーブル                 | 集約値                     | 変化する操作                                           |
| ------------------------ | -------------------------- | ------------------------------------------------------ |
| `transactions`           | 行数、`updated_at`の最大値 | 取引の作成・編集・物理削除                             |
| `recurring_transactions` | 行数、`updated_at`の最大値 | 定期取引の作成・編集・終了                             |
| `categories`             | 行数、`updated_at`の最大値 | カテゴリの追加・名称変更・並び替え・色変更・アーカイブ |

- 物理削除は行数の減少で、編集は`updated_at`の更新で、削除と作成が同じ確認間隔に収まった場合は新しい行の`updated_at`で検出する。
- 集約値を連結した文字列のSHA-256を16進で表し、先頭32文字を変更tokenとする。クライアントへ行数・時刻を渡さない。
- 集約queryはRLSが適用されるユーザーsessionのclientで実行し、`group_id`のindexを使う範囲だけを読む。取引行の本体、負担額、メモは読まない。
- メンバー（`group_members`）とグループ設定（`groups`）の変更は対象外とする。これらは変更頻度が低く、画面遷移で反映される。

### 4.2 Route Handler

```text
GET /api/v1/groups/{groupId}/changes
```

| 結果                                  | status | body                            |
| ------------------------------------- | -----: | ------------------------------- |
| 変更token取得                         |    200 | `{ "token": "<32 hex>" }`       |
| 未認証（session無し・失効）           |    401 | `{ "code": "UNAUTHENTICATED" }` |
| 不正なgroupId、非メンバー、存在しない |    404 | `{ "code": "NOT_FOUND" }`       |

- 応答は常に`Cache-Control: private, no-store, no-cache, must-revalidate, max-age=0`とする。
- 認可は共有読み取り境界`resolveGroupReadContext`で毎回確認し、Route Handler自身はSupabase clientを直接使わない。
- CSV出力Route Handlerと異なり、未認証をログイン画面へredirectしない。`fetch`から呼ばれる前提のため、JSONのerror codeを返す。
- 応答へ取引データ、件数、最終更新時刻、メンバー情報を含めない。

## 5. クライアントの動作

### 5.1 配置と対象画面

- グループ配下のlayoutへ小さなClient Component（変更確認component）を1つ置き、現在のpathnameから自動反映画面かどうかを判定する。
- 自動反映画面は次のpathnameだけとする。

```text
/groups/{groupId}
/groups/{groupId}/history
/groups/{groupId}/analytics
/groups/{groupId}/analytics/details
```

- `/groups/{groupId}/transactions/*`、`/settings`、`/members`、`/categories`、`/recurring-transactions`では変更確認要求を送らない（`SYNC-005`）。
- componentは画面へ何も描画しない。loading表示、バッジ、トーストを追加しない。

### 5.2 確認のタイミング

1. 自動反映画面を開いた直後、およびpathnameが変わった直後に変更tokenを取得し、基準値として保持する。この取得では再取得を行わない。自分の保存後にホームへ戻った場合も、ここで基準値が最新化されるため余分な再取得は発生しない。
2. 画面が表示中（`document.visibilityState === "visible"`）の間、30秒間隔で変更確認を行う。
3. 非表示になったら間隔timerを止める。表示へ戻ったら直ちに変更確認を行う。ただし前回確認から5秒未満なら次回の間隔まで待つ。
4. `navigator.onLine`が`false`の間は確認を行わず、次の間隔で再試行する。

### 5.3 反映

- 取得した変更tokenが基準値と異なる場合、基準値を更新して`router.refresh()`を呼ぶ。同じ場合は何もしない。
- 利用者が入力欄（`input`、`textarea`、`select`、`contenteditable`）へfocusしている間は再取得を保留し、次回の確認で再判定する。履歴の絞り込みformへの入力を巻き込まないためである。
- 再取得はServer Componentだけを再描画する。URLは変更しないため、月・`scope`・`member`・`day`・絞り込み条件はそのまま維持される。route-levelの`loading.tsx`は表示されない。
- ホームの日付選択（`day`）はNative History APIでURLへ同期済みのため、再取得後もserverが同じ日付を検証して日別パネルを維持する。
- 履歴で「さらに読み込む」を使った後（URLに`cursor`がある状態）は、再取得の直前にURLから`cursor`を除いて先頭ページから読み直す。先頭ページの内容が変わっていなければ追加読み込み済みの行を維持し、変わっていれば先頭ページだけを表示して「さらに読み込む」で続きを取得できる状態へ戻す。

### 5.4 失敗時

- 通信失敗・5xxでは画面へエラーを表示せず、次回の間隔を2倍にして再試行する（30秒 → 60秒 → 120秒 → 240秒 → 最大300秒）。成功したら30秒へ戻す。
- 401（未認証）と404（非メンバー・不正ID）では確認を停止する。次の画面遷移で通常の認証・所属確認が働く。
- 再取得中に次の確認時刻が来た場合は重ねて実行せず、次回へ回す。

## 6. 費用と性能

- 変更確認の1要求は集約query 3件だけで、取引行を読まない（`NFR-PERF-007`）。
- 2人が同時に画面を開き続けた場合でも、確認要求は1分あたり最大4件程度で、Cloud Runのrequest-based billingとSupabaseの無料枠に対して十分小さい。
- 非表示中は要求を送らないため、ホーム画面へ戻したスマートフォンから定期的な要求は発生しない。

## 7. 実装境界

| 境界                                   | 提供module | 内容                                                                                                                   |
| -------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| `getGroupChangeToken(groupId)`         | `sync`     | `resolveGroupReadContext`で認可を確認し、集約値から変更tokenを返す。未認証は`unauthenticated`、非メンバーは`not_found` |
| `GroupDataRefresher`                   | `sync`     | 変更確認・再取得を行うClient Component。groups layoutから利用する                                                      |
| 確認方針の純関数（`domain`）           | `sync`     | 自動反映画面の判定、次回間隔のbackoff、表示復帰時の再確認判定、入力中判定                                              |
| `GET /api/v1/groups/{groupId}/changes` | `src/app`  | Route Handler。`sync`の公開エントリ経由で`getGroupChangeToken`を呼ぶ                                                   |

`sync`モジュールはDB行、負担額、金額を扱わず、他機能へ集約値を公開しない。

## 8. 受け入れ条件

受け入れ条件は[`02-use-cases.md`](02-use-cases.md)の`UC-020`（`AC-SYNC-001-1`〜`AC-SYNC-006-2`）を正本とする。

## 9. 対象外・後続

- Realtime subscriptionによる即時反映（`D-010`、`OPEN-006`）
- 変更を知らせるバッジ・トースト・音
- 取引入力・編集画面での競合の事前通知（編集競合は従来どおり保存時の`version`検査で扱う）
- メンバー・権限・グループ設定の変更の自動反映
- Service Workerによるバックグラウンド同期、プッシュ通知
