# ユースケースと受け入れ条件

状態: 承認済み

バージョン: 0.2.21

## UC-001 グループを作成する

操作者: 認証済みユーザー

基本フロー:

1. ユーザーがグループ名を入力する。
2. アプリがJPY、Asia/Tokyo、選択された週の開始曜日、標準負担方法を設定する。
3. グループとowner所属情報を原子的に作成する。
4. 初期カテゴリをグループへ複製する。
5. 作成したグループを選択中にする。

受け入れ条件:

- `AC-GRP-001-1` 未認証の要求を拒否する。
- `AC-GRP-001-2` 正常な要求で、グループ1件とowner所属1件だけを作成する。
- `AC-GRP-001-3` 途中失敗しても、ownerのいないグループを残さない。
- `AC-GRP-001-4` 作成者は直後に新規グループのカレンダーを開ける。
- `AC-GRP-001-5` 別ユーザーは、IDを推測してもグループへアクセスできない。
- `AC-CAT-001-1` 作成したグループに、承認済みの支出7件・収入3件の初期カテゴリを重複なく作成する。

## UC-002 メンバーを招待・追加する

操作者: owner/adminが招待を作成し、認証済みユーザーが承認する。

基本フロー:

1. ownerまたはadminが、追加後の権限を`admin`または`member`から選んで招待を作成する。
2. アプリは暗号学的乱数による256 bit以上のURL-safeな生トークンを生成し、SHA-256 hashだけをDBへ保存する。
3. 生トークンをURL fragmentへ含めた共有リンクを作成結果に1度だけ表示する。有効期限はサーバー時刻から72時間とする。
4. 招待された利用者がリンクを開く。未認証の場合は、同一tabの`sessionStorage`に一時保持してGoogleログイン後に承認画面へ戻る。
5. Server Actionが生トークンの形式と認証を検証し、hashを使ってDB commandを実行する。
6. DB commandが招待行をlockし、有効性と許可済みGoogle identityを再確認して、所属作成または再有効化と招待使用済み更新を原子的にcommitする。
7. 承認後は生トークンを`sessionStorage`から削除し、参加したグループへ遷移する。

受け入れ条件:

- `AC-GRP-004-1` 招待権限のないmemberは招待を作成できない。
- `AC-GRP-004-2` 生トークンは作成時に1度だけ返し、DBにはハッシュだけを保存する。
- `AC-GRP-004-3` 期限切れ、取消済み、使用済みの招待を拒否する。
- `AC-GRP-004-4` 同一ユーザーによる同一招待の再承認は冪等に処理する。
- `AC-GRP-004-5` 承認によって所属情報を重複作成しない。
- `AC-GRP-004-6` 招待リンクはアプリからメール送信せず作成者に1度だけ表示し、許可リスト外のGoogleアカウントは有効なトークンを持っていても承認できない。
- `AC-GRP-004-7` 生トークンは256 bit以上のURL-safeな暗号学的乱数とし、DBにはSHA-256 hashだけを保存する。
- `AC-GRP-004-8` 共有リンクは生トークンをURL fragmentへ格納し、request path、query、cookie、log、永続storageへ含めない。未認証からのログイン継続に使う場合も同一tabの`sessionStorage`だけへ一時保持し、承認成功時に削除する。
- `AC-GRP-004-9` owner/adminだけが保留中招待を一覧・取消でき、招待で`owner`を指定できない。取消の再送は安全に同じ結果を返す。
- `AC-GRP-004-10` 未使用招待を既存のアクティブメンバーが承認した場合は所属を増やさず招待を使用済みにする。削除済みの同一所属がある場合は同じ所属IDを招待roleで再有効化し、過去参照を維持する。

## UC-003 共有支出を登録する

例: メンバーAが食費6,000円を支払い、AとBで均等負担する。

期待結果:

```text
グループ支出: 6,000円
Aの支払額: 6,000円
Aの支出: 3,000円
Bの支払額: 0円
Bの支出: 3,000円
```

受け入れ条件:

- `AC-TXN-001-1` 金額は正の安全な整数でなければならない。
- `AC-TXN-001-2` 支払者と負担メンバーは、同じグループのアクティブメンバーでなければならない。
- `AC-TXN-001-3` 負担額合計は6,000円と一致する。
- `AC-TXN-001-4` 取引と負担額を原子的に保存する。
- `AC-TXN-001-5` 操作者は認証済みユーザーになる。
- `AC-TXN-001-6` カレンダーのグループ合計が6,000円だけ増える。
- `AC-TXN-001-7` AとBの支出がそれぞれ3,000円増える。
- `AC-TXN-001-8` 同じ`client_request_id`を再送した場合、既存結果を返す。
- `AC-TXN-001-9` スマートフォンでは支出カテゴリの名称を常時表示し、選択肢全体を44 x 44 CSS pixel以上のタップ領域として選択できる。選択状態は色だけに依存せず、キーボードでも操作できる。
- `AC-TXN-001-10` 負担方法は1人、均等、カスタムの順に表示し、初期選択は1人とする。均等へ切り替えた場合は全アクティブメンバーを負担者に選択する。
- `AC-TXN-014-1` 金額欄はOSの仮想キーボードを開かず、画面内テンキーの1〜9、0、00で入力し、1文字削除できる。
- `AC-TXN-014-2` 物理キーボードとスクリーンリーダーからも金額を入力・確認できる。
- `AC-TXN-014-3` 金額の入力中も、カテゴリ選択と保存操作を画面内へ表示し続ける。
- `AC-TXN-014-5` テンキーは金額欄へfocusしたときに開き、金額欄以外の入力欄へfocusしたときに閉じる。入力ドック内（カテゴリ・キー・保存）の操作では開閉状態を変えない。
- `AC-TXN-014-6` テンキーを閉じている間も金額欄から再び開けることを画面上の説明で示し、物理キーボードとスクリーンリーダーからの金額入力は開閉状態にかかわらず維持する。
- `AC-TXN-014-7` テンキーを開いたとき、入力中の金額欄が入力ドックへ隠れない位置へ表示する。
- `AC-TXN-014-4` 金額は先頭に0を作らず、安全な整数の上限を超える桁を追加しない。上限や不正な入力は既存の値を壊さない。
- `AC-TXN-015-1` カテゴリは既定で1行に表示し、選択中のカテゴリを常に判別できる。
- `AC-TXN-015-2` 「すべて」を押すと全カテゴリを2列で展開し、キーボードとスクリーンリーダーから到達できる。スワイプだけでしか展開できない操作にしない。
- `AC-TXN-015-3` 展開中にカテゴリを選ぶと1行表示へ戻り、選択したカテゴリを保持する。
- `AC-TXN-016-1` 保存操作は入力ドック内へ常設し、テンキーの開閉とカテゴリの展開のどの状態でも画面から消えず、ドックの高さを増やさない。テンキーを開いている間は数字キーの右列、閉じている間は全幅で表示する。
- `AC-TXN-016-2` 保存中は保存操作を無効化し、二重送信を防ぐ。
- `AC-TXN-015-4` 展開・折りたたみでフォームの他の入力値を失わない。

均等割りの端数規則: JPYの整数へ分割し、余りはmembership IDの昇順で1円ずつ加算する。送信前に計算結果を画面表示する。

支出登録の入力規則:

- 金額は文字列として受け取り、`1`からJavaScriptの安全な整数上限`9,007,199,254,740,991`円までの10進整数だけを許可する。桁区切り、小数、指数表記、符号付き表記は受け付けない。
- 取引日は実在する`YYYY-MM-DD`だけを許可し、初期値はグループのタイムゾーンにおける当日とする。将来日を一律には拒否しない。
- メモは前後の空白を除去して500文字以内とし、空文字は未設定として保存する。
- 「均等」は選択した1人以上のアクティブメンバーへ配分し、「1人」は選択した1人へ全額を配分し、「カスタム」は正の整数で入力した1人以上の負担額を使う。0円の負担行は保存しない。
- 画面で計算した負担額は確認表示に使うが、Server ActionとDB commandは選択メンバー、合計、グループ所属を独立して再検証する。
- 支出登録画面を開いた時点で`client_request_id`を生成し、結果不明の再送では同じ値を使う。成功後に同じ値が再送された場合は既存取引IDを返し、重複登録しない。

## UC-004 グループ内の個人支出を登録する

例: メンバーAが1,200円を支払い、全額をAへ割り当てる。

- `AC-TXN-002-1` グループ支出が1,200円増える。
- `AC-TXN-002-2` Aの支出が1,200円増える。
- `AC-TXN-002-3` Bの支出は変わらない。
- `AC-TXN-002-4` 非公開取引はMVP対象外のため、両方のアクティブメンバーから閲覧できる。

## UC-005 取引を編集する

- `AC-TXN-008-1` 更新には現在のversionが必要である。
- `AC-TXN-008-2` 古いversionによる更新は競合として返し、新しいデータを上書きしない。
- `AC-TXN-008-3` 金額と負担額を一緒に検証する。
- `AC-TXN-008-4` 認証済み操作者と更新日時を記録する。
- `AC-TXN-008-5` カレンダーと履歴に同じ更新結果を表示する。

## UC-006 取引を削除する

- `AC-TXN-009-1` 削除は取引本体と負担行を同じtransactionで物理削除する。
- `AC-TXN-009-2` 削除した取引をカレンダー・履歴・CSVの合計から即時に除外する。
- `AC-TXN-009-3` 未削除の取引への削除は現在のversionと一致する場合だけ実行し、古いversionは競合として拒否する。
- `AC-TXN-009-4` すでに削除済み（存在しない）取引への削除の再送は、状態を変更せず成功として扱う。
- `AC-TXN-009-5` 削除操作と確認dialogは、固定入力ドックと画面下部ナビゲーションに覆われない位置へ表示し、幅320px・375px・1280pxで最下部までscrollすればタップできる。

削除の取り消し・復元機能は提供しない。誤削除への備えは、手動DB dump（NFR-REC-003）とCSV出力を利用者側の運用とする。

## UC-007 月間カレンダーを表示する

- `AC-CAL-001-1` 初期月はグループのタイムゾーン上の当月とする。
- `AC-CAL-001-2` `?month=YYYY-MM`で別の月を選択できる。
- `AC-CAL-001-3` 不正な月指定では未処理例外を出さず、安全な検証エラー状態を表示する。
- `AC-CAL-001-4` グループ対象では各支出を1度だけ数える。
- `AC-CAL-001-5` メンバー対象では、選択メンバーの負担額だけを合計する。
- `AC-CAL-001-6` 削除済み取引と収入を支出合計から除外する。
- `AC-CAL-001-7` 選択月以外の日付を月間合計へ含めない。
- `AC-CAL-001-8` 非メンバーへグループデータを返さない。
- `AC-CAL-001-9` `scope=group`は取引金額、`scope=self`と`scope=member`は対象membershipの負担額を日別・月別に合計する。
- `AC-CAL-001-10` `scope=member`では同じグループのアクティブmembership IDを必須とし、不正・削除済み・別グループのIDへデータを返さない。
- `AC-CAL-001-11` 対象メンバーの月間集計は負担額を「支出」として統一し、支払額を集計領域へ表示しない。
- `AC-CAL-001-12` カレンダーはグループの週開始曜日に従う42セルとし、選択月外のセルへ金額を表示しない。
- `AC-CAL-001-13` `day=YYYY-MM-DD`が選択月内の実在日なら、同日の支出を作成日時の新しい順で表示する。
- `AC-CAL-001-14` 不正な`scope`、`member`、`day`では未処理例外を出さず、取引データを含まない検証エラー状態を表示する。
- `AC-CAL-001-15` 日別・月別合計はJPY安全整数として計算し、浮動小数点による金額計算を行わない。
- `AC-CAL-001-16` 0円でない日別合計は、金額の大小にかかわらず`10,000`のような桁区切り10進数字で正確に表示し、`万`表記への省略や丸めを行わない。
- `AC-CAL-001-17` 同じ月・scope・member内の日付選択と解除は、追加のserver navigationやDB queryを発生させず即時に日別パネルだけを更新する。`day`はURLへ同期し、再読み込み・共有・ブラウザの戻る／進むでも同じ有効な選択を復元する。
- `AC-CAL-001-18` 日別取引sheetの各取引行（単発の支出・収入、定期取引の展開行）は、カテゴリ名とともにカテゴリに設定された色を補助情報として表示する。色は許可済みの色tokenだけを`data-*`属性とCSSで描画し、DBやDTOの色文字列をinline styleやclass名へ組み込まない。色が未定義・許可外でもカテゴリ名を省略せず、既定色で崩れなく表示する。
- `AC-CAL-001-19` 月移動は前月・翌月ボタンと「今日」操作だけで行い、カレンダー本体上の横方向のpointer操作（タッチのスワイプ、マウスのドラッグ）では月を移動しない。横方向のpointer操作は日付セルのタップ、縦スクロール、`AC-CAL-001-17`の即時反映を妨げない。
- `AC-CAL-012-1` 日付セルへ、その日の収入合計を「＋」表記と収入用の色で表示する。収入0円の日には表示せず、色だけで種別を伝えない。
- `AC-CAL-012-2` 収入の集計対象は、`scope=group`では全収入、`scope=self|member`では対象メンバーが受取者の収入とする。
- `AC-CAL-012-3` 月間の収入合計を「収入」と明記した支出とは別の値として表示し、支出合計（CAL-009）へ合算しない。
- `AC-CAL-012-4` 日別取引sheetへ収入取引を種別が分かる形で表示する。収入に負担内訳・対象者の支出額は表示しない。
- `AC-CAL-013-1` 集計領域へ、同じ月・集計対象の支出合計、収入合計、収支差額（収入 − 支出）を表示する。
- `AC-CAL-013-2` 差額は金額の前へ符号（黒字は`＋`、赤字は`−`、0円は`±`）を表示し、符号と数字だけで黒字・赤字が判別できる。
- `AC-CAL-013-3` `scope=self|member`では支出側を対象メンバーの負担額、収入側を対象メンバーが受取者の収入として集計し、差額をその差とする。ラベルはすべての集計対象で「支出」「収入」「収支」に統一し、集計領域へ支払額を並記しない（CAL-010）。
- `AC-CAL-013-4` 収入0円、支出0円、両方0円の月でも例外を出さず、意味の分かる表示にする。
- `AC-CAL-013-5` 差額は最小通貨単位の整数で計算し、浮動小数点を使わない。金額文字列はlocale実装に依存せず、server renderとclient hydrationで一致する。
- `AC-CAL-013-6` 日付選択（`day`）の変更では月間の支出・収入・差額を再取得せず、`AC-CAL-001-17`の即時反映を維持する。
- `AC-CAL-014-1` 表示月が当月と異なる場合だけ「今日」操作を表示し、押すとグループのタイムゾーン上の当月へ移動する。`scope`と`member`は維持し、`day`は付けない。
- `AC-CAL-014-2` 表示月が当月の場合は「今日」操作を表示せず、操作の有無で月移動行・集計領域・カレンダー行の高さと日番号の位置が変わらない。
- `AC-CAL-014-3` 「今日」操作は44 x 44 CSS pixel以上のタップ領域と文字labelを持ち、accessibility nameに移動先の月を含む。
- `AC-CAL-014-4` 当月の判定はサーバーがグループのタイムゾーンで決定した値を使い、端末時刻を使わない。
- `AC-CAL-016-1` 日付セルの日番号は、週開始曜日が日曜・月曜のどちらでも実際の曜日に基づき、土曜日を薄い青、日曜日を薄い赤で表示する。平日には曜日による色を付けず、曜日見出しの文字色・セル背景・金額の色は曜日で変えない。
- `AC-CAL-016-2` 曜日の色は補助情報とし、曜日見出しの文字（土・日）で曜日を判別できる。今日の表示（塗りつぶし）は土日でも維持し、選択日・hover時の表現は変えない。選択月外の土日は弱い表示のまま色相だけを区別する。
- `AC-CAL-016-3` 曜日の色付けで日番号・金額の位置と行の高さを変えない。曜日はサーバー側のグリッド生成で決定した値を使い、Client Componentで`Date`から再計算せず端末のtimezoneに依存しない。

## UC-008 履歴を閲覧・絞り込みする

基本フロー:

1. アクティブメンバーが選択中グループの履歴画面を開く。
2. サーバーが認証・所属・絞り込み条件を検証し、取引一覧と次ページcursorを返す。
3. 利用者が絞り込みを変更するか、「さらに読み込む」で続きを取得する。

受け入れ条件:

- `AC-HIS-001-1` 選択中グループの取引を、取引日の新しい順、同一取引日内は作成日時の新しい順に表示する。
- `AC-HIS-001-2` 削除済み取引を通常の履歴一覧へ表示しない。
- `AC-HIS-001-3` アクティブメンバーでないユーザーへ履歴データを返さない。
- `AC-HIS-002-1` 月、種別、カテゴリ、支払者、受取者、負担メンバーの絞り込みをサーバーで検証し、組み合わせて適用できる。
- `AC-HIS-002-2` 不正な絞り込み値は暗黙補正せず、取引データを含まない検証エラー状態を表示する。
- `AC-HIS-003-1` 「自分の利用」は、現在メンバーへの負担額がある取引を選択する。
- `AC-HIS-003-2` 「自分が支払った」は、現在メンバーが支払者の取引を選択する。
- `AC-HIS-003-3` 2つの絞り込みを異なるラベルで表示する。
- `AC-HIS-003-4` 絞り込みを使っても、所属していないグループを検索できない。
- `AC-HIS-005-1` 一覧は標準30件・最大100件のcursor paginationとし、offset paginationを使用しない。
- `AC-HIS-005-2` 「さらに読み込む」は絞り込み条件を維持したまま次ページを取得し、行を重複・欠落させない。

## UC-009 CSVを出力する

- `AC-EXP-001-1` 選択中グループと指定された絞り込み範囲だけを出力する。
- `AC-EXP-001-2` 取引日、種別、金額、カテゴリ、支払者または受取者の表示名、負担内訳、メモを含める。
- `AC-EXP-001-3` ユーザー入力文字列の表計算ソフト数式プレフィックスを無害化する。
- `AC-EXP-001-4` ファイル名に、安全な形式へ変換したグループ名と期間を含める。
- `AC-EXP-001-5` 認可されていない出力要求へデータを返さない。

## UC-010 収入を登録する

例: メンバーBが給与300,000円を受け取る。

- `AC-TXN-013-1` 収入には、選択グループのアクティブな受取者が1人必要である。
- `AC-TXN-013-2` MVPの収入に支出用の負担額を設定できない。

## UC-012 登録・ログイン・セッションを管理する

基本フロー:

1. ユーザーが通常のtop-level navigationでGoogleログイン開始Route Handlerへ遷移する。
2. Googleが本人確認し、Supabase AuthがPKCE callbackを処理する。
3. 登録前フックがGoogle providerと許可リストを照合し、対象外はAuthユーザー作成前に拒否する。
4. 許可された初回ログインでSupabase Authのユーザーと`profiles`行を作成する。
5. アプリがcookieのsession、Google provider、許可リストを再検証し、保護画面を表示する。
6. ユーザーがログアウトするとsessionを破棄し、ログイン画面へ戻る。

受け入れ条件:

- `AC-AUTH-001-1` 未認証画面はGoogleログインだけを表示し、メールアドレス、ID、パスワード、OTPの入力欄を表示しない。
- `AC-AUTH-001-2` GoogleログインはPKCE callbackでcodeをsessionへ交換し、callback後のredirectは構成済みの公開サイトoriginと許可済みの相対pathからだけ生成する。Auth cookieを設定する応答は共有cacheへ保存させない。
- `AC-AUTH-001-3` 許可された初回ログイン時、認証ユーザーと同じIDの`profiles`行を1件だけ作る。
- `AC-AUTH-001-4` OAuth失敗、許可対象外、Auth停止を区別した安全なメッセージを表示し、tokenやproviderの内部詳細を表示しない。
- `AC-AUTH-001-5` 初回プロフィールの表示名は、Googleが返す検証済みmetadataの`full_name`、`name`、「ユーザー」の順で最初の空でない値を使い、前後空白を除去して50文字以内にする。
- `AC-AUTH-001-6` OAuth認可URLは、生成元が構成済みの内部または公開Supabase originで、pathが`/auth/v1/authorize`の場合だけ、構成済みの公開Supabase originへ変換してブラウザへ返す。Docker内部hostname、想定外origin・path、認証情報またはfragmentを含むURLを拒否する。
- `AC-AUTH-001-7` OAuth開始Route Handlerは検証済みの戻り先だけを受け付け、PKCE verifier cookieを応答へ設定した後に公開Supabase認可URLへredirectする。Googleからアプリへ戻ったcallbackは同じcookieを使ってcodeをsessionへ交換でき、cookie欠損時はsessionを作らず安全なOAuth失敗として扱う。
- `AC-AUTH-001-8` OAuth開始要求のoriginが構成済みの公開サイトoriginと異なる場合、PKCE cookieを発行せず、検証済みの戻り先だけを含む公開サイトorigin上のOAuth開始Routeへredirectする。canonical originへ揃えた後の応答でPKCE cookieを発行し、callbackと同じhostへ保存する。
- `AC-AUTH-001-9` ブラウザに失効済みまたは無効なAuth cookieが残った状態でOAuthログインを完了した直後でも、保護画面の初回表示をserver errorにしない。Proxyは認証境界（`/auth`配下のRoute Handler）に対してsession refreshを行わず、Server Componentの読み取りqueryは認証起因の失敗（期限切れ・無効JWT）をserver errorとして扱わず、未認証としてログイン誘導へ合流させる。
- `AC-AUTH-001-10` access tokenの期限が切れた後も、refresh tokenが有効な間は再ログインを求めない。session更新を行った境界は、rotate後のtokenを同じ応答のcookieへ書き戻し、ブラウザが保持するtokenと不一致にしない。
- `AC-AUTH-001-11` 認証済みで`start_url`（`/`）またはOAuth開始Routeへ到達した場合、ログイン画面とGoogle認証を経由せず、ホームまたは検証済みの戻り先を表示する。
- `AC-AUTH-001-12` 失効したAuth cookieが残った状態でも、1回のGoogleログインでsessionが成立する。callbackは既存のsession cookieを参照せずPKCEのcode verifierだけでcodeを交換し、交換したsession cookieを同じ応答内の削除cookieで打ち消さない。
- `AC-AUTH-001-13` 認証済みでホーム（`/app`）を開く要求では、プロフィールとグループ一覧の取得完了を待たずにroute shellとskeletonを先に返し、ホーム画面インストール版の起動直後を含めて全面が白いままの状態を作らない。skeletonは`aria-busy`で読み込み中を伝え、確定後の画面と同じ配置（header、プロフィール、グループ一覧）と375px・1280pxのカラム構成を保つ。
- `AC-AUTH-002-1` ログインユーザーは自分のプロフィールを取得・更新でき、別ユーザーとして更新できない。
- `AC-AUTH-003-1` ログアウト後は保護画面を閲覧できず、ログイン画面へ遷移する。
- `AC-AUTH-004-1` 未認証で保護画面へアクセスすると、ログイン後の戻り先を安全な相対pathとして保持してログイン画面へ遷移する。
- `AC-AUTH-004-2` 外部URL、protocol-relative URL、制御文字を含む戻り先を拒否し、標準の保護画面を使う。
- `AC-AUTH-004-3` サーバーの重要な読み取り・更新は、cookie上の未検証session情報ではなく検証済みclaimsまたはAuthユーザーを使用する。
- `AC-AUTH-005-1` ユーザー向けコードからメール・パスワード登録、ログイン、再設定の画面と処理を削除する。旧URLはログイン画面へ安全に転送する。
- `AC-AUTH-005-2` Authのメール、電話番号、匿名ログインを無効化し、ローカル・本番のアプリ構成からSMTPとMailpitを除外する。
- `AC-AUTH-005-3` 許可リストは大文字小文字と前後空白を正規化して重複のない有効なメールアドレス1件以上を受け付け、件数の上限を設けない。不正値、重複、空値を含む場合は全件を無効にする。Git、クライアントbundle、log、画面に値を公開しない。

- `AC-ANA-009-2` 320px幅と375 x 812では横スクロールが発生せず、支出・収入・収支と月移動を片手で操作できる。横スクロール式のカード列を使わない。
- `AC-ANA-009-3` 1280 x 800では同じ情報構造と同じ値を保ったまま利用可能幅へ適応し、コンテンツが過度に横へ伸びない。
- `AC-ANA-010-1` 収入を支出合計、メンバー負担額、メンバー支払額のいずれへも混入させず、別ラベルで表示する。
- `AC-ANA-011-1` 予算値がない月は予算進捗領域を表示せず、予算値がある場合だけ消化額・残額・消化率を同じDTO境界から表示する。
- `AC-ANA-012-1` 概要分析と期間サマリーは同じ認可済み集計サービスを共有し、同じグループ・期間・対象に対して同じ金額を返す。
- `AC-ANA-012-2` 24か月を超える期間、不正な月、開始月が終了月より後の期間サマリー要求をfail closedで拒否し、取引を読み込まない。

## UC-018 所属グループが1件のときホームから直行する

操作者: アクティブな所属グループを1件だけ持つログインユーザー。

基本フロー:

1. 利用者がログインを完了する、`start_url`を開く、またはホーム（`/app`）へ遷移する。
2. サーバーが認証済みsessionからアクティブな所属グループを取得する。
3. 所属が1件だけであれば、グループ一覧を表示せずにそのグループの当月・グループ全体のカレンダーへ遷移する。
4. 所属が0件または2件以上であれば、従来どおり作成画面または一覧を表示する。
5. グループ一覧・プロフィール・グループ作成が必要な場合、利用者は設定の「グループを切り替える・作る」など明示的な導線から一覧表示を開く。

受け入れ条件:

- `AC-GRP-011-1` アクティブな所属が1件だけのユーザーが`/app`を開くと、一覧を表示せずに`/groups/{groupId}`（当月・グループ全体）へ遷移する。ログイン完了後の既定の戻り先、認証済みでの`/`・ログイン画面からのホーム転送も同じ結果になる。
- `AC-GRP-011-2` 所属が0件のユーザーには従来どおりグループ作成画面、2件以上のユーザーには従来どおりグループ一覧を表示し、直行しない。
- `AC-GRP-011-3` グループ一覧を明示的に開く導線（設定の「グループを切り替える・作る」、履歴の「グループ一覧」）は`/app?view=groups`へ遷移し、所属が1件でも一覧・プロフィール・グループ作成を表示する。
- `AC-GRP-011-4` 遷移先の判定はサーバー側で認証済みsessionから取得した所属だけを使い、クライアントから渡されたgroupIDや件数を信用しない。`view=groups`以外のquery値は一覧表示への切替として扱わず、既定の判定に従う。
- `AC-GRP-011-5` 直行先のカレンダー画面は従来どおり認証・所属を再確認し、遷移の間に所属を失った場合も他グループの存在や内容を明かさない。

## UC-019 詳細分析で期間の変化と内訳を確認する

操作者: アクティブメンバー。

基本フロー:

1. 概要分析から詳細分析を開く。
2. 3・6・12か月のpreset、または開始月と終了月を選ぶ。
3. グループ全体、自分、指定メンバーから対象を選ぶ。
4. 期間合計、月平均、最大支出月、月別推移、カテゴリ構成を確認する。
5. グループ対象では、各メンバーの負担額・支払額・受取額を比較する。
6. グラフと同じ値を月別の数値表で確認する。

受け入れ条件:

- `AC-ANA-006-1` 未指定時は当月を終了月とする直近6か月を表示し、3・6・12か月presetと1〜24か月の任意範囲を選択できる。
- `AC-ANA-006-2` 期間と集計対象をURLへ保持し、再読み込み・URL共有でも同じ条件と値を表示する。
- `AC-ANA-006-3` 不正な月、逆順、24か月超は取引を読み込まずにfail closedで拒否し、既定の6か月表示へ戻る導線を示す。
- `AC-ANA-007-1` グループ全体、自分、同一グループのアクティブメンバーを対象にでき、メンバー対象の支出は負担額として集計する。
- `AC-ANA-007-2` 別グループまたは削除済みmembership、scopeと一致しないmember指定を拒否し、分析値と存在を取得できない。
- `AC-ANA-008-1` 期間の支出・収入・収支合計は月別値の合計と一致し、平均支出は取引0円の月を含む期間月数で割ってJPY整数へ四捨五入する。
- `AC-ANA-008-2` 最大支出月は期間内の月別支出から求め、同額は新しい月、全月0円は「該当なし」とする。
- `AC-ANA-008-3` カテゴリ別支出は期間全体をカテゴリIDで集計し、全カテゴリの合計が期間支出と一致する。アーカイブ済みカテゴリも含める。
- `AC-ANA-008-4` グループ対象では各アクティブメンバーの負担額・支払額・受取額を別系列で表示し、各列を混在させない。self・member対象では重複する比較領域を表示しない。
- `AC-ANA-009-4` 月別推移の支出・収入・符号付き収支を正確なJPY数値表でも表示し、装飾グラフ、hover、色がなくても値と意味を理解できる。
- `AC-ANA-009-5` 320px・375 x 812では横スクロールなしで主要操作を44 x 44 CSS pixel以上にし、数値表を月別行へ適応する。1280 x 800では同じ順序・値を保って複数カラムへ適応する。
- `AC-ANA-012-3` 詳細分析は概要・期間サマリーと同じ認可済み月次集計を使い、1要求で月次取引を1回だけ読み込む。同じ期間・対象の金額は一致する。
