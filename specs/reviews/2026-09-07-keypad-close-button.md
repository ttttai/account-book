# 取引入力の金額テンキーへ「閉じる」キーを追加する

状態: 実装確認済み
レビュー日: 2026-09-07
ブランチ: feat/keypad-close-button
対象仕様: `specs/01-product-requirements.md`、`specs/02-use-cases.md`、`specs/03-screen-specification.md`、`specs/07-acceptance-test-plan.md`、`specs/08-decisions-and-deferred-scope.md`
関連ID: `AC-TXN-014-8`・`AC-TXN-014-9`を追加（`TXN-014`の文言を更新。要件IDの追加なし）

## 指摘

- 取引入力のテンキー（`TXN-014`）は金額欄以外の入力欄へfocusしたときだけ閉じるため、金額を入力し終えて下部のフォーム（取引日、支払者、負担方法、メモ）を広く見たい利用者は、閉じるためにどこか別の入力欄をタップして開いてから戻る必要があった。OSの仮想キーボードが持つ「閉じる」に相当する明示的な操作がない。
- 閉じるキーを追加する場合、行を追加すると入力ドックが高くなり`AC-TXN-014-7`・`AC-TXN-016-1`・`AC-TXN-017-6`（ドックを高くしない）と衝突する。右列（1文字削除・=・保存）へ入れると保存の高さが半分になり、主要操作の面積を削る。
- キーを押した直後にキー自身が消えるため、focusが`body`へ落ちてスクリーンリーダーの読み上げ位置と物理キーボードのTab順が失われる。閉じたあとのfocus先を決めないと実装が推測で処理することになる。
- 閉じるキーの文言を「閉じる」にすると、カテゴリ展開の「閉じる」（`AC-TXN-015-3`）と同名のボタンが同じ画面に存在する。表示上は展開中にテンキーを隠すため同時には出ないが、E2Eの`getByRole("button", { name: "閉じる" })`は部分一致のため、名前の設計とテストの一致条件を揃える必要がある。

## 対応

- `AC-TXN-014-8`（閉じるキーの挙動）と`AC-TXN-014-9`（配置とタップ領域）を追加し、`TXN-014`と画面仕様の開閉条件へ「閉じるキーを押したとき」を加えた。
- 配置は数字キーの最下行の左端（00の左）とし、最下行を「閉じる」、00、0（電卓有効時はその右に+）にする。00と0の並びは従来どおり変えない。0は現在2列分の幅を持つが、OSの数字キーボードでは0は1列幅が通常であり、00キーが別にあるため入力効率は落ちない。行を追加しないためドックの高さは変わらず、保存も右列の下2行のまま維持する。
- 閉じた直後のfocusは金額欄へ置く。金額欄には閉じている間の再開案内（`AC-TXN-014-6`）が`aria-describedby`で結び付いているため、スクリーンリーダーには「金額欄をタップするとテンキーを開きます」がそのまま伝わり、Tabで次の入力欄（取引日）へ進める。このfocus移動でテンキーを開き直さないよう、閉じる操作の中で行うfocusだけは開く判定を抑止する。以後の金額欄のタップ・再focusは従来どおり開く。`focus({ preventScroll: true })`でscroll位置を動かさない。
- 表示文言は「閉じる」、アクセシブルネームは`aria-label="テンキーを閉じる"`とする（表示文言を含むためLabel in Nameを満たす）。E2Eの共通操作はカテゴリ展開の「閉じる」を`exact: true`で取り、テンキーの「テンキーを閉じる」と区別する。component test（Testing Library）は既定で完全一致のため影響しない。
- 共有部品`AmountKeypad`は`onClose`propを任意指定で受け取り、指定時だけ閉じるキーを描画し、0の2列幅を解除する。固定費・予算フォームは指定しないため表示・挙動を変えない。両フォームへの展開は`08-decisions-and-deferred-scope.md`の延期機能へ記録した。
- 閉じるキーは数字と押し間違えにくいよう、演算子キーと同系の控えめな背景と小さめの文字にする。320pxでも「閉じる」が1行に収まる大きさへ落とす。

## 安全性確認

- Server Action、schema、DB、認可、楽観的ロックは変更しない。閉じるキーは`type="button"`でフォームを送信せず、金額の式状態（`amountExpression`）と送信値（hidden input）に触れない。
- 閉じた直後のfocus移動は金額欄（同一フォーム内の既存input）だけを対象とし、OSの仮想キーボードは`inputmode="none"`のため開かない。
- 開閉状態のみを変えるためデータ再取得や画面全体の再描画は発生しない（局所的な状態変更）。

## 実装可能性確認

- `ExpenseForm`の`keypadOpen`と`handleFormFocus`、`AmountKeypad`の`DIGIT_ROWS`描画、`.keypad-key[data-key="0"]`のCSSだけで実装できる。
- 幅375px（ドック内幅約351px、電卓有効時の数字4列）では各数字キーが約60px、320pxでも約50pxで、「閉じる」を0.85rem前後の文字で1行に収められる。44 x 44 CSS pixel以上は既存の`.keypad-key`の`min-height: 48px`（PCでは44px）で満たす。
- architecture test（`transactions-foundation.test.mjs`）は`onClose`の任意指定と固定費・予算が指定しないことを構造で検証できる。

## MVP範囲確認

- 対象は取引入力のみ。固定費・予算は延期機能へ記録した。スワイプで閉じる操作、キーの長押し、開閉のアニメーション、開閉状態の永続化は含めない。新しい依存packageやmigrationは追加しない。

## 判定

`AC-TXN-014-8`・`AC-TXN-014-9`は`TXN-014`・`TXN-015`・`TXN-016`・`TXN-017`、`AC-TXN-014-5`〜`AC-TXN-014-7`、`AC-TXN-016-1`、`AC-TXN-017-6`、`NFR-UI-001`・`NFR-UI-002`・`NFR-UI-004`、`NFR-A11Y-*`と整合し、安全かつ実装可能である。`ExpenseForm`のcomponent test（閉じるキーで閉じる、金額と式を失わない、focusが金額欄へ移りテンキーが開かない、再focusで開く、フォームを送信しない）、固定費・予算のテンキーに閉じるキーが出ないcomponent test、architecture testを先に追加し、実装後に320px・375 x 812・1280 x 800で閉じるキーが00・0・+と重ならず、ドックが高くならないことを実画面確認する条件で実装開始を承認する。
