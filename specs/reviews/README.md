# 仕様レビュー記録（1レビュー1ファイル）

`specs/09-spec-review.md`は`R-001`〜`R-077`までの記録として凍結し、それ以降の仕様レビューは本ディレクトリに1レビュー1ファイルで記録する。複数のworktreeが同じファイルの末尾へ同時に追記して衝突する構造をなくすための運用である。

## ファイル名とID

- ファイル名は`YYYY-MM-DD-<slug>.md`とする。日付はレビュー日、`<slug>`はブランチ名の内容部分（`feat/group-invitation`なら`group-invitation`）を小文字のkebab-caseで書く。
- レビューIDはファイル名の拡張子を除いた部分（例: `2026-09-03-split-spec-review`）とする。連番（`R-078`など）は採番しない。mainへ入る順序に依存させないためである。
- PR本文、コミットメッセージ、コード内コメントからは`review: 2026-09-03-split-spec-review`の形で参照する。
- 本ディレクトリの一覧表やインデックスは作らない。一覧はディレクトリのファイル名で足りる。追記式の一覧は再び衝突源になる。
- 同じ機能を再レビューする場合は、古いファイルを書き換えず新しい日付のファイルを追加し、本文で旧レビューIDを参照する。

## 必須項目

各ファイルは次の見出し構成にそろえる。`09-spec-review.md`の各`R-`項目と同じ観点である。

```markdown
# <レビュー題名>

状態: 下書き | 承認済み | 実装確認済み
レビュー日: YYYY-MM-DD
ブランチ: <種別>/<内容>
対象仕様: <変更した仕様ファイル>
関連ID: <要件ID・受け入れ条件ID。追加した場合は「追加」と明記。追加しない場合は「追加なし」>

## 指摘

## 対応

## 安全性確認

## 実装可能性確認

## MVP範囲確認

## 判定

## 実装確認
```

- `状態`は、仕様レビューの承認で`承認済み`、実装・検証の完了で`実装確認済み`へ更新する。
- `判定`に実装開始の条件（先に作るテスト、確認する画面幅など）を書く。
- `実装確認`はテスト件数、lint・型検査・buildの結果、375pxと1280pxの実画面確認を書く。実装前は空のままでよい。
- 要件ID・受け入れ条件IDの一意性は`tests/architecture/foundation.test.mjs`が仕様ファイルから直接検証する。件数を`09-spec-review.md`へ追記しない。
